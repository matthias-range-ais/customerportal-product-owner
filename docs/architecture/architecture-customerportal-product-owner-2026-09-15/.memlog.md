- 2026-09-15 direction: User refined the per-call write-confirmation constraint (SPEC.md) into a staged **Plan/Apply model**: domain logic proposes a list of pending write operations (POST/DELETE) against EquipmentCloud as plain data (target endpoint + JSON payload); user reviews the list, can optionally open an individual item to inspect its endpoint/payload; then confirms the whole batch; only then are the calls executed in sequence. Reason given: no trust yet in what gets executed automatically. Supersedes the SPEC.md wording "shown ... and explicitly confirmed before execution" (per-call) with a batch-plan variant — to reconcile back into SPEC.md at Finalize.
- 2026-09-15 decision: Paradigm — domain/core logic is kept free of HTTP/EquipmentCloud/DB specifics; write side-effects are represented as data (planned operations) produced by the core and executed only by a separate adapter after confirmation (ports-and-adapters style boundary, refined by the Plan/Apply write model). User confirmed this fits.
- 2026-09-15 decision: Plans (the list of pending, unexecuted operations) are ephemeral — no persistence required across app sessions; built and confirmed within one sitting.
- 2026-09-15 decision: Data ownership split — for CAP-1 (SoftwareCenter), EquipmentCloud is the sole source of truth; no independent local persistence is required, a rebuildable cache is enough. From CAP-2 onward, the tool will build up genuinely first-party local data (personally relevant groupings/information that has no EquipmentCloud counterpart and is never synced back) — this is owned locally, not a cache of anything.
- 2026-09-15 direction: Since CAP-1 needs no real persistence, the choice of local DB engine (incl. the CAP-2 graph/relationship requirement) is deferred as architecture seed, not fixed now — revisit when CAP-2 work starts.
- 2026-09-15 decision: Deployment/operational envelope — the tool runs purely locally as a single Node process on the Product Owner's own Windows machine (started manually, used via a browser against localhost); no server deployment, no multi-machine access.
- 2026-09-15 constraint: The local DB file's storage location must be user-configurable; the user intends to point it at a personal mapped network drive (Z:) for backup/safety once persistence is actually needed (from CAP-2 onward).
- 2026-09-15 question: SQLite (and similar embedded engines) are known to be unreliable over network-mounted drives on Windows (file-locking issues) — needs checking against whichever DB engine is chosen when CAP-2 starts; may require writing locally and syncing/backing up to Z: instead of opening the DB file directly over the network share. Flagged for the reviewer gate / revisit at CAP-2.
- 2026-09-15 decision: Apply-failure handling — when executing a confirmed plan, execution halts immediately at the first failed operation; remaining operations in the plan are not attempted, so the user can inspect the error before deciding how to proceed.

- 2026-09-15 decision: Single-process model — one Fastify server serves both the built React frontend (static) and the tool's own JSON API from one process; one start command, one port. No separate frontend/backend processes for normal use.
